### 1.2 CKKS 編碼、權重量化與 CRT 空間

- 訊息縮放 Δ = 2³⁰；雲端用整數權重 w_int = round(w·2³⁰)，所以輸出縮放為 2⁶⁰。解碼器以 Δ² 還原。
- 量化誤差上限：特徵數 × 8 × 0.5/2³⁰ ≈ 10⁻⁸，可以忽略。
- 和 Q/2 相比，最大的 |y|·2⁶⁰ 加上最壞雜訊後，還剩 **21–24 bits 空間**（ai4i 22.1、進展 23.6、症狀 21.1）。不會發生 CRT 回繞。
- 硬體輸入條件 |m| < 2⁶² 由驅動在 DMA 之前檢查；C01 會在板上驗證這一點。

### 1.3 雜訊與精度：理論、模擬與板上實測一致

解密後的雜訊為 Σ_f w_f·(e·u_f + e0_f + e1_f·s)，其中 s、u 是均勻三元，e、e0、e1 是 σ = 4.5 的高斯。

| | ai4i | 進展 | 症狀 |
|---|---:|---:|---:|
| 解析模型：每個 slot 的標準差 | 4.25×10⁻⁵ | 1.06×10⁻⁵ | 5.55×10⁻⁵ |
| 蒙地卡羅（81,920 個 slot）標準差 | 4.26×10⁻⁵ | 1.06×10⁻⁵ | 5.55×10⁻⁵ |
| 蒙地卡羅：81,920 個 slot 中的最大值 | 3.2×10⁻⁴（7.4σ） | 8.3×10⁻⁵ | 3.7×10⁻⁴ |
| **每窗口一把金鑰的模擬：窗口最大值中位數** | **3.90×10⁻⁴** | **9.85×10⁻⁵** | — |
| **板上 6 小時長測：窗口最大值中位數** | **3.94×10⁻⁴** | **9.67×10⁻⁵** | — |
| 板上 p90／模擬 p90 | 4.36×10⁻⁴／4.14×10⁻⁴ | 1.08×10⁻⁴／1.15×10⁻⁴ | — |
| 驗收容許值 | 2×10⁻³ | 5×10⁻⁴ | 2×10⁻³ |

**重要發現**：slot 誤差的尾巴比高斯厚。

- 原因：解碼是在根上求值，屬於環同態，所以 (e·u)(ζ) = e(ζ)·u(ζ)，每個 slot 的誤差是「兩個近高斯量的乘積」之和。
- 而 e(ζ)、s(ζ) 由金鑰決定，在整個程序內固定。
- 因此用「6σ」估最大誤差會低估約 1.7 倍。正確做法是依每把金鑰計算精度證書（系統裡的 B04 `ef_owner_error_bound`），或用上面的金鑰窗口模擬。
- 這也解釋了 campaign v3 中，症狀模型有 25 筆超過 5×10⁻⁴：它們都在 2×10⁻³ 的容許值以內，原因就是理論預期的尾部。

**結論**：板上量到的誤差可以完全由 CKKS 雜訊數學解釋。窗口最大值中位數的模擬與實測，ai4i 相差 1%、進展相差 2%。沒有證據顯示硬體有額外誤差。

### 1.4 精度還能怎麼提升（未採用，只列選項）

- 誤差 ≈ ‖w‖·雜訊 / Δ。如果 Δ 改成 2³⁵，誤差約小 32 倍，CRT 空間仍有約 16 bits。
- 代價：精度設定改變後，量化、精度證書、精確 PL 檢查和所有原件都要重新驗收。目前的誤差已在容許值以內，所以不建議為此改動已接受的設定。

## 2. 架構審查

| 層 | 現況 | 評估 |
|---|---|---|
| 信任分界 | 私鑰與明文只在 KV260；雲端只拿到密文與公開模型身分；TLS 1.3 雙向憑證＋釘選 | ✅；限制見 [B02](security/SECURITY_ASSESSMENT_zh-TW.md)：metadata、側信道、完整性 |
| PS／PL 分工 | ARM：正規化、FFT 編碼、解密、CRT；PL：取樣（ChaCha20＋CDT63）與 3 limb × 4 lane NTT 加密 | 符合提案；同板 PL 加密比 OpenFHE 快 9–11 倍、比 CPU3 快 2.7–3.3 倍 |
| 裝置安全 | 每次呼叫都要 permit（綁定開機、父程序、執行檔、參數）；租約有世代管理；不合法的框在 DMA 前就被拒；出錯即隔離本次開機，不自動重試 | ✅；C01 會在板上逐項驗證 |
| 吞吐瓶頸（實測） | 滿槽窗口中，PL 路徑的主執行緒（準備＋解密，約 7.8 ms）忙碌 85–88%，網路執行緒（約 8.3 ms）忙碌 78–79% | 兩者都接近飽和，詳見第 3 節 |
| 程序與執行緒限制 | owner 函式庫規定加解密只能由建立它的執行緒呼叫；裝置也只有一個 DMA 擁有者 | 解密不能直接移到另一條執行緒，必須改 owner 函式庫並重新驗收 |
| 雲端（PC） | Windows 原生程式，單一連線、依序處理；運算中位數 0.12 ms | 不是瓶頸；即時展示中偶發約 16 ms 的量化尖峰，疑為 Windows 計時器 |

## 3. 加速與吞吐最佳化：依數據排序

| 代號 | 內容 | 預期效益（依實測推算） | 公平性 | 狀態 |
|---|---|---|---|---|
| O1 | 管線深度 2 → 3／4 個 slot（只改用戶端） | 吸收抖動、讓準備和網路更平行；IO 已接近飽和，預期增益不大 | CPU／PL 用同一設定 | ✅ 已實作，**S1b 上板 A/B** |
| O2 | 即時展示的暫存檔改放 tmpfs | 每筆省約 14 ms（已實測） | 兩邊都受益 | ✅ 已上板 |
| O3 | 網路執行緒全雙工：上傳第 i+1 筆的同時下載第 i 筆 | 每筆 IO 約 8.3 → 7 ms，吞吐約 +20%（要等 S1 剖析確認） | 兩邊都受益 | 設計中，看 S1 結果再決定 |
| O4 | 請求雜湊（SHA-256，ai4i 每筆 384 KiB）改用硬體加速或移出主執行緒 | 取決於 S1 量到的 A53 SHA-256 成本 | 兩邊都受益 | 等 S1 數據 |
| O5 | 解密改成獨立的管線階段 | 主執行緒每筆少 2.8 ms → PL 吞吐可能 +35% 以上 | 兩邊都受益 | 需要改 owner 函式庫並重新驗收；排在 O3 之後 |
| O6 | PC 伺服器提高計時器解析度（timeBeginPeriod） | 去掉約 16 ms 的偶發尖峰（改善 P95 與即時展示） | 兩邊都受益 | 需要重建 Windows 伺服器；可選 |

原則：每項最佳化都是**隔離的候選版本**，CPU 與 PL 套用同樣的改動，以 A/B 實測決定是否採用。只靠推算不宣稱效益。

## 4. 方法流程審查

- **做得好的地方**：
  - 以 session 為單位做 bootstrap；
  - CPU 基準和 PL 用同樣的最佳化；
  - 同次開機比較；
  - 獨立的審查程式不採信板端自報數字；
  - 每個子程式都核對中斷數 = DMA 次數；
  - 原件封存並附雜湊；
  - 一次開機只發一個 intent，不自動重送。
- **限制**（需要寫進報告）：
  - 單板、單次開機；
  - 信賴區間是邊際區間，沒有做多重比較校正；
  - 網路只測過一台 PC 和一台路由器；
  - 功耗只量 SOM 供電軌。
- **建議**：
  - 最終報告附上 M1、C01、S1 的原件；
  - 精度以「每金鑰證書＋金鑰窗口模擬」說明，不要用高斯 6σ；
  - 吞吐最佳化以 S1b 的 A/B 結果為準。

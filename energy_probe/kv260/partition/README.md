# 軟硬體切分：ARM 逐模組實測與 PL 估計

本資料夾把 EdgeFHE 客戶端的工作拆成最小模組，在同一次量測中實測每個模組在 ARM 的時間與整板能量，並實測 FPGA 的可程式邏輯（PL）整段加密的時間與能量；PL 各階段的時間依 HLS 原始碼估計。本資料夾再以這些數字比較不同的軟硬體切分方式。能量一律取自外接探針（[../../README.md](../../README.md)）量測的 KV260 整板 12 V 輸入。

## 檔案

| 檔案 | 內容 |
|---|---|
| [module_bench.cpp](module_bench.cpp) | 板上程式。以 V8b 的 CPU 規格程式（`baseline/core.cpp`、`sampler_b.hpp`，輸出與 PL 逐位元一致）實作每個模組。`bench [次數]` 輸出每個模組的中位數時間（JSON）；`loop <模組> <秒數> [執行緒數]` 連續執行單一模組，供探針量測。 |
| [partition_measure.py](partition_measure.py) | 電腦端量測流程。經 KV260 主控台建立 `~/partition`、上傳並編譯 `module_bench`，先以單核執行 `bench 40`，再載入 V8b，依序量測：待機 30 秒、各模組單核 8 秒、3 個模組 4 執行緒、PL 的 k 掃描與連續加密（k = 8、1）、共同執行（CPU 1–3 正規化與編碼＋CPU 0 驅動 PL）、全部在 ARM（4 執行緒）。每個區間以探針的 `B`／`E` 指令標記；結束時卸載 V8b 並恢復 `k26-starter-kits`。`bench` 的原始輸出完整保存在 `partition_runs.json` 的 `bench_raw`。 |
| [analyze_partition.py](analyze_partition.py) | 分析。計算待機基準、各模組的時間與多耗的能量、PL 的呼叫成本、三種切分方式、各段的處理能力上限與每批往返的工作量；輸出 `partition_summary.json` 與 `figures/fig_p1`–`fig_p4`。 |
| [hls_model/](hls_model/hls_stage_estimates.md) | PL 各階段的估計：HLS 原始碼的迴圈次數 × 啟動間隔，加上管線深度與資料流排程模型。`hls_stage_estimates.json` 供 `analyze_partition.py` 讀取。 |

## 執行

1. 探針接在 COM5、KV260 主控台接在 COM6，且同一時間只有本程式使用這兩個序列埠。
2. 板上需有 `~/EdgeFHE_repo`（本 repository，提供 CPU 規格程式；可在板上以 `git clone --depth 1 <本 repository 的網址> ~/EdgeFHE_repo` 取得）與 `~/edgefhe-v8b-r5`（V8b 板上套件），並已安裝 `g++-11`。上傳與編譯使用的 `~/partition` 由程式自動建立；上傳或編譯失敗時，程式立即停止。
3. 以環境變數 `KV_PW` 提供板子的登入密碼（不要寫進檔案），執行 `python partition_measure.py <輸出資料夾>`。全程約 6 分鐘，輸出 `probe.csv` 與 `partition_runs.json`。
4. `python analyze_partition.py <輸出資料夾> hls_model/hls_stage_estimates.json`
5. 報告：`python ../make_report.py <10 輪資料夾> [同日 3 輪資料夾] [未接乙太網路資料夾] --partition=<輸出資料夾>` 會在 V8b 與 OpenFHE 的比較報告中加入「軟硬體切分」一章。

## 定義

- **ARM 時間**：CPU 規格程式在 1 顆核心上處理一個密文的平均時間。一次性的設定（金鑰、公鑰頻譜與 NTT 表）在計時前完成，不計入。
- **多耗的能量**：（模組執行時的整板平均功率 − 待機功率）× 每個密文的時間。待機為 V8b 已載入、不執行任何工作的狀態。
- **PL 路徑**：`board_enc_check sustain` 連續加密時每個密文的牆鐘時間，包含驅動的複製、檢查、快取同步與清除。**PL 核心**：驅動的 `dma_hls` 階段 ÷ 8，只含 DMA 與 HLS 核心。
- **PL 各階段（估計）**：[hls_model/](hls_model/hls_stage_estimates.md) 的每個密文時間。ARM 的三元遮罩模組自行產生遮罩所需的 16 個 ChaCha20 區塊，因此三元遮罩一列的 PL 值取 `prng_mask` 與 `sample_ternary` 之和。
- **共同執行**：3 顆核心（CPU 1–3）連續執行正規化與編碼，同時 CPU 0 驅動 PL 連續加密；兩者為獨立程式，PL 加密自己的測試資料。系統速度取兩者中較慢者，每焦耳筆數以兩者同時執行時的整板功率計算。
- **筆數**：1 個密文 = 512 筆（每個密文 2048 個 slot，每筆 4 個特徵）。

## 限制

- ARM 端為 CPU 規格程式，未使用 V8b 應用程式的 Harvey NTT、N/2 點 FFT 的編碼與解碼，以及解密的 NTT(s) 快取；應用程式另以 3 執行緒平行處理單一密文（縮短延遲，不減少核心時間）。公鑰頻譜在本次量測中已快取，全部在 ARM 以 4 執行緒平行處理不同密文。應用程式的 ARM 成本會較低，因此上述瓶頸只適用於以 CPU 規格程式計的加密上行路徑，不代表端到端的瓶頸。
- PL 各階段的時間為依 HLS 原始碼的估計；整段時間為實測。排程模型預測每 frame（k = 8）1,056.9 µs，本次實測的 `dma_hls` 為 1,074.4 µs，相差 1.6%（[hls_model/hls_stage_estimates.md](hls_model/hls_stage_estimates.md) 另以同日 10 輪比較中一次呼叫的 1,075.3 µs 對照）。此一致性只驗證瓶頸的模數引擎鏈，非瓶頸階段（m 轉 RNS、三元遮罩、CDT63、ChaCha20）的估計未經實測驗證。實測 `dma_hls` ÷ 8 = 134.3 µs 是任一 PL 階段每個密文平均時間的上限；除三元遮罩與 m 轉 RNS 外，其餘模組的 ARM 單核時間皆高於此上限，因此這些模組在 PL 較快不依賴估計。
- 共同執行以兩個獨立程式近似 V8b client：PL 以全速加密（每秒 3,225 個密文），比正規化與編碼（每秒 2,328 個）多做約 39% 的工作；實際管線中 PL 約有 28% 的時間閒置。以 PL 單獨執行時的功率增量按比例估計，多做的工作約多耗 0.25 W，使實測的每焦耳筆數低估約 2%，因此結果略為保守。共同執行時 PL 每次呼叫由 2.25 ms 增為 2.48 ms。
- 每種設定量測 1 次（模組 8 秒、PL 15 秒、共同執行與全部在 ARM 各 30 秒），倍數未附信賴區間。時間與以總功率計的每焦耳筆數，重複性可參考 10 輪比較（30 秒區間的變異係數 0.2–0.5%）；以功率增量計的模組能量（單核模組的增量約 0.2–0.4 W），相對不確定度較大，約數個百分點。
